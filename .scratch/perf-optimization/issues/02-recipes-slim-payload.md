# 菜谱载荷与列表渲染的进一步瘦身

Status: needs-triage

## 背景

性能专项后，菜谱相关请求已合并为每资源一条，但载荷本身仍是全量：

1. `useRecipes` 拉全表 `select('*')`——包括 `ingredients` / `steps` 大列，
   而列表行与筛选只需要标题、分类、分钟数、收藏、cooked、封面、标签。
2. 菜谱详情页从这份全量里 `find(slug)`；深链冷启动要等全表。
3. 菜谱库是 `ScrollView` + `.map` 全量渲染，百道菜以上滚动与内存才开始吃力
   （个人规模几十道时无感）。

## 候选方案（互相独立，可分批做）

- **列表瘦身**：列表查询收窄列集，详情页单独按 slug 拉全量行（数据层已有事件机制可复用）。
- **FlatList 化**：菜谱库换 `FlatList`（featured 卡做 ListHeader），StaggerItem 错峰保留前 N 项。
- **服务端聚合**：stats 的 2000 行上限若将来不够，改 RPC 聚合（现在个人规模够用）。

## Comments

- 2026-10-25 · 性能专项审计时记录，本轮不做（当前数据规模收益小、动 UI 结构风险高）。
